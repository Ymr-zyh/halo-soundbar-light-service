# Halo SoundBar Max 氛围灯 Windows 服务设计

日期：2026-10-18

## 1. 背景与已验证事实

目标设备是花再（EDIFIER）Halo SoundBar Max。设备在电脑关机后仍保持氛围灯点亮，因此需要一个独立于 EDIFIER TempoHub 的 Windows 服务，在系统启动时打开全部氛围灯，并在 Windows 进入关机流程、收到 `SERVICE_CONTROL_PRESHUTDOWN` 时关闭全部氛围灯。

本设计基于参考项目 `Seraph310/halo-pixelbar-mcp`、本机 TempoHub 1.3.1 的静态资源和字节码分析，以及对真实设备的只读查询和可回滚开关测试。已确认：

- 目标设备身份为 VID `0x2D99`、PID `0xA073`、接口号 `4`、Usage Page `0xFF14`、Usage `0x0001`、产品名 `EDIFIER Halo Soundbar Max`。
- 氛围灯查询命令为 `0x6A`，设置命令为 `0x6B`。
- 当前设备的灯组编号为 `0x0C`；主机氛围灯开关索引为 `0x0B`，低音箱氛围灯开关索引为 `0x0C`。
- 官方程序的单灯开关载荷为 `[灯组编号, 开关索引, 0, 0, 开关值, 0xFF, 0xFF]`。该命令只改变开关字段，不改变效果、颜色、亮度或速度。
- 在真实设备上直接发送开、关命令后，查询结果显示效果编号和索引 `0x01` 到 `0x0A` 的样式数据保持逐字节不变；恢复打开后完整状态与初始状态一致。
- 每次 `0x6B` 写入可能产生一个 `0x6B` 应答和两包 `0xE3` 完整状态数据，因此实现不能假设“一写一读”，必须先清理陈旧响应，并按分包序号收集状态。

## 2. 目标

服务必须实现以下行为：

1. 作为自动启动的 Windows 服务运行。
2. 服务启动后，在 USB 设备可用时打开主机和低音箱的氛围灯。
3. 收到 `SERVICE_CONTROL_PRESHUTDOWN` 后，在系统关机前关闭主机和低音箱的氛围灯。
4. 标准 `SERVICE_CONTROL_SHUTDOWN` 作为兼容性回退，也执行关灯。
5. 手动停止服务仅停止服务进程，不改变灯光状态。
6. 所有开关操作只修改两个已确认的开关字段，不改变现有灯效样式或参数。
7. 在设备身份或协议状态与预期不一致时拒绝写入，避免误操作其他 HID 设备或未知固件。
8. 提供 `probe`、`on`、`off` 命令，便于安装前验证和故障排查。

## 3. 非目标

- 不修改、注入、替换或终止 EDIFIER TempoHub。
- 不控制灯效模式、颜色、亮度、速度、音乐律动或屏幕取色。
- 不支持未验证的其他 Halo 产品、PID 或 HID 接口。
- 不在服务中持续轮询或强制覆盖用户在 TempoHub 中选择的灯效。
- 不把关机或重启电脑作为自动化测试的一部分；真实关机验证必须在用户明确同意后单独执行。

## 4. 技术方案

采用 Python 3、pywin32 和 hidapi 实现，并通过 PyInstaller 打包为自包含的单文件可执行程序。

选择该方案的原因：

- pywin32 能直接实现 Windows Service 控制处理，包括扩展接受 `SERVICE_ACCEPT_PRESHUTDOWN`。
- hidapi 与参考项目及 TempoHub 的 HID 通信模型一致，且已在本机真实设备上验证可用。
- 本机已有可用的 Python、pywin32、pytest 和 PyInstaller 环境；没有安装 .NET SDK。
- 单文件交付不要求目标运行时保留 Python 环境。

服务以 LocalSystem 账户运行，启动类型设为 Automatic。安装程序设置服务描述、失败自动重启策略和 15 秒的 Preshutdown 超时时间。

## 5. 组件划分

计划采用以下目录结构：

```text
src/halo_soundbar_service/
  protocol.py       HID 帧构造、校验和状态分包解析
  device.py         严格设备发现、打开、读写和响应队列管理
  controller.py     查询、开关、验证、重试和样式不变性检查
  service.py        Windows Service 生命周期与控制码处理
  cli.py            probe/on/off/install/uninstall 命令入口
  logging_setup.py  Windows 事件日志和滚动文件日志
tests/
  test_protocol.py
  test_device.py
  test_controller.py
  test_service_lifecycle.py
scripts/
  build.ps1
  install.ps1
  uninstall.ps1
```

`protocol.py` 和 `controller.py` 保持与 Windows Service API 解耦，以便在不触发系统关机的情况下进行完整单元测试。

## 6. HID 协议

### 6.1 主机发送帧

报告总长为 64 字节，结构如下：

```text
2E AA ED <command> <length-high> <length-low> <payload...> <checksum> <zero padding...>
```

校验和为从 `AA` 开始到载荷末尾的所有字节之和对 256 取模。首字节 `2E` 是 HID Report ID，不参与校验。

四条唯一允许的写命令为：

```text
主机关闭: 2E AA ED 6B 00 07 0C 0B 00 00 00 FF FF 1E
主机打开: 2E AA ED 6B 00 07 0C 0B 00 00 01 FF FF 1F
低音箱关闭: 2E AA ED 6B 00 07 0C 0C 00 00 00 FF FF 1F
低音箱打开: 2E AA ED 6B 00 07 0C 0C 00 00 01 FF FF 20
```

以上前缀之后补零至 64 字节。实现不接受调用方提供任意载荷，而是通过受限的 `build_power_packet(target, enabled)` 生成，以保证不会构造修改样式的命令。

### 6.2 状态查询与解析

查询使用命令 `0x6A`。设备以两个 `0xE3` 分包返回完整状态。每包载荷前四字节为：

```text
[总分包数=2, 分包序号, 灯组编号=0x0C, 当前效果编号]
```

其后为六字节条目：

```text
[索引, R, G, B/开关值, 亮度, 速度]
```

解析器必须校验帧头、命令、声明长度、校验和、总分包数、分包序号和灯组编号。分包按序号合并，允许应答包和陈旧状态包穿插出现，但在限定时间内未得到一组完整、有效且相互一致的状态时视为失败。

## 7. 严格设备发现

只打开同时满足以下全部条件的 HID 路径：

- VID 为 `0x2D99`
- PID 为 `0xA073`
- 接口号为 `4`
- Usage Page 为 `0xFF14`
- Usage 为 `0x0001`
- 产品名为 `EDIFIER Halo Soundbar Max`

如果没有匹配设备，操作返回“设备未就绪”；如果出现多个完全匹配的设备，默认逐个读取并仅对能通过协议探测的设备操作，但若两个以上设备同时通过探测则拒绝写入并记录歧义，避免一次控制多个未明确授权的设备。

首次写入前必须完成 `0x6A` 查询，并确认：

- 灯组编号为 `0x0C`；
- 存在索引 `0x0B` 和 `0x0C`；
- 两个开关条目的固定字段为 `R=0`、`G=0`、`亮度=0xFF`、`速度=0xFF`；
- 开关值只可能为 `0` 或 `1`。

任一条件不满足时采用 fail-closed 策略：不发送任何 `0x6B` 写命令。

## 8. 单次开关操作流程

每次启动开灯或关机前关灯均执行同一事务流程：

1. 获取进程内互斥锁，保证同一时刻只有一个灯光事务。
2. 枚举并严格匹配设备，打开一个短生命周期 HID 会话。
3. 以短超时循环读取，清空会话中已排队的陈旧应答。
4. 发送 `0x6A`，收集两个有效 `0xE3` 分包，形成操作前快照。
5. 校验设备协议结构和两个开关条目；不符合即退出且不写入。
6. 若两个开关已经处于目标状态，则记录幂等成功并退出。
7. 仅对状态不匹配的开关发送对应的固定 `0x6B` 命令。
8. 清理写入产生的 `0x6B` 应答和附带状态包，再次主动执行 `0x6A` 查询。
9. 确认两个开关达到目标值，并确认效果编号以及索引 `0x01` 到 `0x0A` 的原始条目逐字节不变。
10. 若未达到目标状态，在总时间预算内重新查询并重试，最多三轮。
11. 关闭 HID 会话，释放互斥锁，记录最终结果。

写入顺序固定为主机 `0x0B` 后低音箱 `0x0C`。中途失败时不尝试构造“恢复样式”命令，因为服务从未写入样式；它只重新查询并补发尚未达到目标状态的开关命令。

## 9. Windows Service 生命周期

### 9.1 接受控制码

服务继承 pywin32 的 `ServiceFramework`，覆盖接受控制码的计算结果，在标准 STOP 和 SHUTDOWN 基础上加入：

```text
SERVICE_ACCEPT_PRESHUTDOWN = 0x00000100
```

`SvcOtherEx` 识别：

```text
SERVICE_CONTROL_PRESHUTDOWN = 15
```

收到该控制码后进入不可逆的服务内部 `shutdown_requested` 状态，取消尚未完成的启动重试，并执行关灯事务。重复的 PRESHUTDOWN 或后续 SHUTDOWN 调用共享同一幂等结果，不并发访问设备。

### 9.2 启动

服务尽快报告 RUNNING，然后在工作线程中执行开灯。考虑到 Windows 启动早期 USB 枚举可能尚未完成，设备未就绪时采用有上限的退避重试：初始 1 秒，之后不超过 5 秒一次，总计不超过 120 秒。

如果期间收到 STOP、PRESHUTDOWN 或 SHUTDOWN，启动重试立即取消。启动开灯最终失败不会导致服务不断崩溃或无限重启，而是记录明确错误；服务继续等待控制事件，以便关机时仍可再次尝试访问设备。

### 9.3 预关机

收到 PRESHUTDOWN 后：

1. 将服务状态报告为 STOP_PENDING，并提供 15 秒 wait hint。
2. 取消启动开灯任务并等待其释放 HID 事务锁。
3. 在最多 12 秒的内部预算内执行关灯、查询验证和有限重试，预留时间给服务管理器完成收尾。
4. 无论成功或失败，都记录结果并退出服务主循环；不能因 USB 故障无限阻塞系统关机。

标准 SHUTDOWN 走同一关灯路径，作为旧系统、服务控制异常或 PRESHUTDOWN 未送达时的回退。

### 9.4 手动停止

`SERVICE_CONTROL_STOP` 只设置停止事件、取消启动任务并退出，不发送开灯或关灯命令。这样管理员重启或升级服务不会意外改变用户当前灯光状态。

## 10. 并发与 TempoHub 共存

服务不依赖 TempoHub 是否运行，也不修改其文件或进程。真实设备验证表明两者可以分别打开 HID 接口，但仍可能在极短时间内交错发包。因此：

- 每次服务操作使用短生命周期会话；
- 写入前后都主动查询；
- 忽略与当前查询不匹配的陈旧分包；
- 以最终查询结果而非单个 ACK 判断成功；
- 样式快照发生变化时，如果变化并非本服务命令能够造成，则记录为外部并发修改，不把它误判为协议写坏；开关目标仍以最终状态判断。

服务不会长期占用或独占 HID 设备。

## 11. 错误处理与日志

关键事件写入 Windows Application Event Log，同时写入：

```text
%ProgramData%\HaloSoundbarLightService\service.log
```

文件日志使用 UTF-8、单文件最大 1 MiB、保留 3 个轮转文件。日志包含服务版本、操作类型、设备匹配结果、查询/验证结果、重试次数和错误类别，但默认不输出整包原始数据，避免日志噪声。`probe` 的显式详细模式可以输出脱敏后的十六进制协议摘要。

错误按以下类别区分：设备未找到、多个设备歧义、身份不匹配、协议校验失败、读取超时、写入失败、验证未达目标、样式快照冲突和内部异常。

## 12. 命令行与安装

同一可执行程序提供：

```text
HaloSoundbarLightService.exe probe
HaloSoundbarLightService.exe on
HaloSoundbarLightService.exe off
HaloSoundbarLightService.exe install
HaloSoundbarLightService.exe uninstall
HaloSoundbarLightService.exe debug
```

- `probe` 只读枚举、查询并显示目标设备和两个开关的当前状态。
- `on`/`off` 使用与服务相同的安全事务，便于安装前验证。
- `install` 需要管理员权限，将程序安装到 `%ProgramFiles%\HaloSoundbarLightService`，注册 Automatic 服务，配置描述、失败重启策略和 15000 ms Preshutdown 超时。
- `uninstall` 需要管理员权限，停止并删除服务注册；只有在用户明确执行卸载时才删除已安装目录，项目源码和日志不自动删除。
- `debug` 在控制台前台运行服务逻辑，便于观察启动流程，但不会伪造真实 Windows PRESHUTDOWN。

构建脚本固定依赖版本并使用 PyInstaller `--onefile`，包含 pywin32 服务运行所需的隐藏导入。构建产物附带 SHA-256 摘要，便于确认安装文件未变化。

## 13. 测试策略

### 13.1 单元测试

- 四条开关帧的完整 64 字节内容和校验和必须与已验证值一致。
- 查询帧、长度、校验和、零填充和非法参数拒绝。
- `0xE3` 两分包乱序、重复、缺包、陈旧包、ACK 穿插和超时处理。
- 错误帧头、错误长度、错误校验和、错误灯组和未知开关值必须失败关闭。
- 严格设备身份匹配以及零个、一个、多个匹配设备的处理。
- 控制器只允许写入索引 `0x0B`、`0x0C` 的开关帧。
- 已处于目标状态时不写入。
- 部分成功、读取超时和最多三轮重试。
- 验证前后样式数据保持不变。
- 生命周期路由：启动到 `on`、PRESHUTDOWN 到 `off`、SHUTDOWN 回退到 `off`、手动 STOP 不操作灯光、重复关机通知幂等。

### 13.2 本机集成测试

在不安装服务前依次执行：

1. `probe` 确认严格匹配唯一设备并读取当前状态。
2. 保存完整灯效状态快照。
3. `off`，确认两个开关为 0，其他状态逐字节不变。
4. `on`，确认两个开关为 1，其他状态逐字节不变。
5. 构建单文件 EXE，并对打包后的 `probe/off/on` 重复测试。
6. 安装服务，确认启动类型、接受控制码和 PreshutdownTimeout 配置正确。

真实关机测试会使电脑关机，必须在用户明确确认执行时间后进行。测试前先确认未保存工作和恢复路径；开机后检查事件日志，验证 PRESHUTDOWN 已触发且关灯成功，再确认服务启动后重新开灯。

## 14. 验收标准

以下条件全部满足后，功能才视为完成：

- 所有自动化测试通过。
- 打包后的 `probe` 能唯一识别 Halo SoundBar Max，且不会选择同设备的其他 HID 接口。
- 打包后的 `off` 和 `on` 能控制主机与低音箱两组灯，查询验证成功。
- 开关往返前后，效果编号和索引 `0x01` 到 `0x0A` 的状态保持不变。
- Windows 服务注册为 Automatic，并明确接受 PRESHUTDOWN。
- 服务启动时可在 USB 延迟枚举情况下最终打开两组灯。
- PRESHUTDOWN 路径在时间预算内关闭两组灯，失败时不阻塞关机且留下可诊断日志。
- 手动停止服务不会改变灯光状态。
- 未通过身份或协议校验时不会发送任何写命令。
- 经用户同意完成一次真实关机/开机验证，或由用户明确接受只完成等效控制码测试而暂不进行真实关机。

## 15. 回滚方案

若服务行为不符合预期，可通过管理员命令停止并卸载服务。卸载不会改动 TempoHub，也不会修改设备固件。移除服务后，音响恢复为完全由 TempoHub 或设备自身控制。由于服务只发送易失性的开关命令，不写固件、不写注册表中的设备配置，也不保存或覆盖灯效样式，因此回滚不需要恢复设备协议数据。
